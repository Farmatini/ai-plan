# Инструкция AI агенту

## Назначение

Этот локальный холст нужен, чтобы **человек понимал устройство программы, которую пишет AI агент**, на любом языке: C++, C#, JavaScript, Python и других. Показывай, из каких систем состоит проект, какие сущности находятся внутри и как они взаимодействуют. Человек должен уметь отдалиться для обзора систем и приблизиться для чтения конкретных сущностей.

Редактором может пользоваться и сам человек. Встроенной модели, обращения к API, автоматического анализа репозитория и синхронизации с IDE здесь нет. AI агент читает исходники и поддерживает `.canvas` как обычный файл проекта. Не обещай, что схема обновляется сама.

## 1. Сначала изучи проект

Прочитай корневые инструкции проекта, README, индекс кода и относящиеся к задаче исходники. Найди канонический файл схемы: путь задан в `config.js` как `canvasPath`, относительно папки редактора. Не путай его со сгенерированным `initial-data.js` и черновиком браузера.

Сохраняй существующее расположение, ID, цвета и подписи, когда они ещё верны. Не удаляй пользовательские правки ради перерисовки всей карты. Если читаешь восстановленный файл пользователя, сначала проверь его и только потом меняй.

## 2. Группа — система, блок — конкретная сущность

Создавай подписанную группу для каждой зоны ответственности: например, «Инвентарь», «Персонаж», «Сетевая логика». Внутри размещай отдельные блоки для классов, скриптов/модулей, структур данных, таблиц, перечислений (enum), компонентов и иных значимых сущностей.

Каждую самостоятельную сущность, относящуюся к изображаемой системе, показывай отдельно. Если в одном файле несколько классов или перечислений, у них разные блоки и один и тот же путь к файлу. В процедурном или функциональном проекте показывай именованные функции и модули вместо выдуманных классов. Для крупного класса можно выделить важные методы отдельно; не превращай каждую временную локальную переменную в блок. Поля и полный API остаются в карточке кода.

Маленький учебный пример может показывать только часть символов: явно подпиши его границы. В рабочей карте не пропускай реальные сущности заявленной системы без объяснения. При слишком большом объёме сначала покажи системы, затем постепенно дополняй их деталями.

Текст блока оформляй так (обычный текст, без расчёта на Markdown-разметку):

```
ТочноеИмяСимвола — тип сущности
РЕАЛИЗОВАНО / ПЛАН / ПРЕДЛОЖЕНИЕ.
Короткое назначение на русском: какие данные получает, что делает, что отдаёт.
Файл: относительный/путь.ext
Карточка: путь/к/описанию.md (если есть)
```

В плановом блоке явно указывай, что символа и файла ещё нет. Не выдавай опору движка, предполагаемый класс или учебный пример за собственную реализацию. Цвет означает **тип**, а статус записывается текстом.

## 3. Цвета и легенда

Назначай цвет каждой сущности по её типу. Не выдавай случайный цвет каждому экземпляру: одинаковые типы должны читаться одинаково. Предложенная начальная палитра:

| Цвет | HEX | Значение |
|---|---|---|
| Зелёный | `#76bc87` | Класс / объектный компонент |
| Оранжевый | `#e4a35c` | Скрипт / модуль / именованная функция |
| Голубой | `#75bed0` | Структура / модель данных / таблица / определение |
| Фиолетовый | `#b596e0` | Enum / набор именованных вариантов |
| Розовый | `#d88b9c` | Внешняя служба или хранилище |
| Серо-синий | `#8a9bb0` | Описание интерфейса, настройка, пояснение |

Если данные и таблицы нужно различать, введи отдельные цвета и обнови легенду. Существующую согласованную палитру проекта сохраняй. Названия типов всегда дублируй текстом: понимание не должно зависеть только от цвета.

На самом холсте делай отдельную группу **«Легенда»** с небольшими цветными блоками-образцами. В них пишется расшифровка: «Зелёный — классы», «Фиолетовый — перечисления» и так далее. Эти образцы — пояснения, не сущности программы. Человек может приблизить и изменить их подписи и цвета. При смене цвета образца реальные блоки автоматически не перекрашиваются: агент должен согласованно изменить их тоже.

## 4. Два уровня связей

**Внутри одной группы:** соединяй конкретные блоки. На стрелке пиши смысл: «вызывает», «читает», «создаёт», «проверяет», «передаёт команду», «возвращает результат». Например, `InventoryComponent → ItemInstance` с подписью «хранит экземпляры предметов».

**Между разными системами:** веди стрелки **от группы к группе**, а не между отдельными блоками этих групп. Например, «Инвентарь → Персонаж: применяет экипировку» и «Инвентарь → Сетевая логика: запрашивает подтверждение операции». При необходимости точные символы-участники укажи в подписи или описании группы. Не проводи длинные межсистемные стрелки через множество внутренних карточек.

Легенду к зависимостям не подключай. Не соединяй группу с её же содержимым только ради обозначения принадлежности: это уже показывает рамка. Направление должно иметь понятный смысл; две стрелки в разных направлениях допустимы, если описывают разные взаимодействия. Не делай двунаправленную связь просто потому, что системы знакомы друг с другом.

Стрелки не доказывают владение объектом, порядок выполнения, сетевую репликацию или RPC. Если связь означает что-то из этого, подпиши это явно и проверь исходник.

## 5. Как менять файл

Поддерживается подмножество JSON Canvas: `text` и `group` в `nodes`, связи в `edges`. Не добавляй файловые и ссылочные узлы: этот редактор их не открывает. Описание исходника помещай в текст.

- У каждого узла и связи уникальный постоянный строковый `id`. Ссылки используют ID, а не заголовок.
- Узел: `id`, `type`, целые `x`, `y`, `width`, `height`. Для текста добавь `text`, для группы — `label`. Цвет задаётся полем `color` вида `#RRGGBB`; доступны также номера палитры `"1"`–`"6"`.
- Группы располагай в массиве раньше текстовых блоков. Членство задаётся геометрически: блок полностью лежит внутри рамки. Отдельного `parentId` нет. Оставляй место для подписи и внутренних связей.
- Связь: `id`, `fromNode`, `toNode`, стороны `fromSide`/`toSide` (`top`, `right`, `bottom`, `left`), подпись `label`; окончания `fromEnd`/`toEnd` равны `none` или `arrow`.
- Для межсистемной связи в `fromNode` и `toNode` указывай именно ID групп. Для внутренней — ID блоков одной группы.
- Не перекрывай соседние карточки, подписи и важные линии. Проверяй общий вид и читаемость при приближении. У названий групп уже есть ограничение увеличения на масштабе 23%; не обходи его индивидуальным огромным шрифтом.

После правки канонического файла запусти `node sync-example.cjs` из папки редактора. Скрипт обновит `initial-data.js`. Затем `node verify.cjs` проверит формат, стартовую копию, ссылки документации и соглашение о связях эталонной схемы. `node smoke-test.cjs` запускает браузерные проверки, если доступен Playwright; подробности — в TESTING.md.

Агенту не требуется щёлкать каждый блок в браузере: структурированный файл удобнее редактировать программно. В конце открой результат для визуальной проверки, если менялось расположение или оформление, и кратко сообщи человеку, что изменилось.

## 6. Сохранение и сопровождение

Обновляй карту вместе с кодом: добавился класс — добавь блок; изменились связи — исправь стрелки; удалена сущность — убери её и зависимые линии. Сохраняй легенду актуальной. Проверяй реальные имена, пути, статусы и направления связей.

Файл `.canvas` — источник схемы. Кнопка «Скачать .canvas» создаёт файл в загрузках: человек должен заменить им канонический файл проекта. Автоматический браузерный черновик — отдельное удобство, не гарантированная резервная копия. Изменение JSON агентом не обновляет уже открытую вкладку автоматически: нужно заново открыть файл или обновить стартовый пример и вкладку. При этом не теряй несохранённый черновик человека.

Не помещай в публичную схему пароли, токены, приватные адреса или ненужные абсолютные пути с именем пользователя. Для GitHub используй относительные пути.

## Пример для игры

«Инвентарь» содержит зелёный `InventoryComponent`, голубую `ItemInstance` и фиолетовый `ItemType`. Внутренние стрелки объясняют хранение и тип предмета. От рамки «Инвентарь» идут подписанные стрелки к рамкам «Персонаж» и «Сетевая логика». Эти имена — учебная иллюстрация, а не подтверждение, что такие классы уже написаны в текущем проекте.

Такое же правило работает для приложения: «Заказы», «Пользовательский интерфейс», «Оплата», «Хранение данных». Язык реализации не меняет назначение холста: объяснять человеку устройство создаваемой программы.
